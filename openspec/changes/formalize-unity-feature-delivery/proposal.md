# Proposal

## Why

The frozen framework describes bounded code execution but does not yet connect
OpenSpec planning, observable parallel TDD, a prepared Unity presentation layer,
and human acceptance into one reproducible delivery lifecycle. Capture these
boundaries before rebuilding the superseded wireframe so a passing test suite is
not confused with a complete, accepted Unity experience.

## What Changes

- Make Codex with OpenSpec the Architect and delegate apply execution through
  versioned JSON contracts and a local executor invocation; retain separate
  planning verification, spec synchronization, and archive responsibilities.
- Add task/unit mappings, explicit test relationships, and evidence that can
  implicate multiple units without a dossier-level defect classification.
- Prepare placeholder artwork, scenes/prefabs, compilable component shells,
  serialized bindings, and an artist replacement manifest before contract freeze.
- Enforce independent test authoring, validity review, observed Red, Green, and
  verified Refactor for every active implementation unit.
- Isolate coding work in per-unit worktrees and serialize coordinator integration
  and Unity EditMode verification against immutable, identified snapshots.
- Keep all game-module coding/integration worktrees outside Unity-imported trees;
  verify candidates in a complete dedicated Unity host containing exactly one
  candidate module and fixed shared-framework dependencies.
- Onboard the existing nested monopoly repository with a non-expandable write
  boundary at Assets/JJGame/monopoly/, existing design/wiki/OpenSpec inputs, and
  versioned coding restrictions; preserve all shared host source and settings.
- Reuse the installed Unity Operator HTTP Bridge for this target and provide a
  game-local, request-specific EditMode test command with durable completion
  evidence. Keep Bridge polling internal to the blocking verification transport.
- Add status, progress, durable results, transaction recovery, budget continuity,
  and a revision-specific human acceptance gate.
- **BREAKING design revision:** permit explicit Architect-controlled ownership
  migrations between contract versions while retaining historical unit records.
- **BREAKING design revision:** automatic success becomes ready-for-review;
  constraint flush and final task completion require human acceptance.
- Propose superseding decisions for test attribution, retry timing, presentation
  integrity, and recovery. Preserve existing settled entries and reconcile docs/
  before implementing any conflicting runtime behavior.

## Capabilities

### New Capabilities

- `architect-execution`: delegated apply, runtime contract lifecycle, task and
  test mappings, design/wiki provenance, target write boundaries/coding profiles,
  version-boundary ownership migrations, and boundary outcomes.
- `presentation-baseline`: placeholder preparation, component shells, frozen
  scene/prefab bindings, integrity checks, and final-art replacement contracts.
- `parallel-tdd`: test validity, independent authoring and freeze, per-unit TDD,
  external module worktrees, candidate materialization into a complete fixed host,
  serialized integration/verification, and evidence attribution.
- `execution-lifecycle`: durable status, recovery, budgets, cancellation, human
  acceptance, Bridge identity/reload handling, durable test completion, review
  feedback routing, and completion provenance.

### Modified Capabilities

None. There are no existing OpenSpec capability specs. These new planning deltas
describe both retained requirements and proposed extensions; they do not silently
supersede docs/.

## Impact

This change plans the overall framework across handoff Phases 0-7 and new
presentation/acceptance milestones. It is not a claim that any phase is complete.
The implementation plan first adopts superseding documentation, then follows the
handoff foundation order with offline fakes before real Unity/model integration.

Affected boundaries include contract/dossier formats, adapter and transport
interfaces, graph state transitions, coordinator workspace management, the Unity
verification worker/Bridge client, game-local test-command packaging, and a new
delegated apply skill. The current source and test wireframes
must be replaced, not extended as a reference implementation.

No schema customization, new dependency, runtime code, target game artwork,
Unity project, or edits to authoritative docs are delivered by this proposal.
Automated PlayMode tests, remote workers, final-art production, and automatic
mainline commits/merges/pushes are excluded. Acceptance is defined by the four
delta specs and the staged checklist, including offline framework tests, graph
compilation, a later scratch-Unity demonstration, and revision-bound human review.

Target onboarding is grounded in the existing game's independent nested Git
repository, Editor-only NUnit test assembly, PSD/prefab tooling, and HTTP Bridge.
It records Tuanjie/HybridCLR restrictions and reuses existing framework services.
All game-specific facts live in the target profile or Unity adapter, never core.
Host provisioning and test-command installation are later authorized deployment
steps, not effects of generating these artifacts. Live Bridge and test execution
were not established by the read-only inspection.
