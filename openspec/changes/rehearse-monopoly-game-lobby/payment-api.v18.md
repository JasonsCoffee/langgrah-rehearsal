# Payment and VIP preparation, cycle 18

These are nonfunctional API and data declarations prepared from the actual
cycle-17 dossier. Configured workers must implement behavior and author all
assertions. Existing selected test IDs and effective assertions remain required.

- `BeginCheckout(accountId, productId, operationId)` creates a pending fake-server
  order. Products are `ingots:<zero-based-tier>` or `card:<card-id>`. Both order IDs
  are generated by the fake service, with the configured price captured in the
  order. The client neither constructs these IDs nor supplies an amount.
- `ApplyPaymentCallback(callback)` correlates game order ID, platform order ID and
  product ID. Status is `paid`, `cancelled` or `failed`. Mismatches cannot deliver;
  duplicates deliver once per correlated order, across persistence restarts.
  Paid delivery failures create one persisted reconciliation task;
  `ReconcilePayments()` retries delivery without double credit. No real payment
  backend is contacted. Existing synchronous convenience APIs must use the same
  service path, retaining their approved outcomes and operation idempotency.
- `world.PaymentDeliveryAllowed` is a fake-backend failure-injection hook, null
  meaning normal delivery. `world.ExchangeCommitAllowed` is called after tentative
  mutation and before commit, null meaning normal commit; false rolls the whole
  exchange back. These are service test seams, never client-supplied outcomes.
- Shell `PendingPaymentOrderId` and `PaymentLoading` expose pending checkout state.
  Existing product-row and confirmation UI actions open a pending checkout. Add
  `SimulatePayment` as an Editor rehearsal/test control (paid/cancelled/failed),
  resolving that checkout through the service callback; expose it in the review
  panel. Preserve all serialized UI action names in binding-protocol.v2.md;
  tests must establish true pending state before success/cancel/failure, and assert
  actual rendered state and wallet transitions, not a constant false property.
- `PlatformVipSnapshot` optionally supplies a fake-platform VIP snapshot. Null hook
  uses the fake platform calculation; a hook returning null simulates unavailable
  data and must be handled safely by the client. Distinct supplied data must be
  observable without client recomputation. The normal service retains the approved
  rolling six-month rules and levels. Browsing levels renders the catalog benefits
  for that level and locks based on the supplied current level.
- `VipBenefitCatalog` plus `LocalizedText` are the rehearsal localization table.
  The seven original benefit categories remain, with level 6/7 adding reward
  bonus. All text is original Monopoly rehearsal copy. VIP remains informational;
  no fee discount or benefit changes a balance, entry fee or reward. Tests should
  mutate a private catalog translation to a unique sentinel and observe its
  rendered value, proving the real data path rather than scanning for prefixes.
